# 第 9 章　連結器與載入器

> **本章目標：** 理解連結器如何合併多個目的檔、解析符號、執行重定位，以及載入器如何將可執行檔對應到記憶體並啟動執行。涵蓋靜態連結、動態連結、共享程式庫的完整機制。

---

## 9.1 連結器的角色

### 9.1.1 為什麼需要連結器？

現代程式由多個模組組成，每個模組獨立編譯（或組譯）產生目的碼（.o），連結器負責將它們合併成一個可執行檔。

```
main.o    ──┐
lib_a.o   ──┤   連結器（ld）   →   程式（可執行檔 / .so）
lib_b.o   ──┤
libc.a    ──┘

連結器的三大任務：
  1. 符號解析（Symbol Resolution）：
       找出每個 UNDEF 符號的定義在哪個目的檔
  2. 重定位（Relocation）：
       將每個目的碼中的相對位址改為最終的絕對位址
  3. 合併區段（Section Merging）：
       把所有 .o 的 .text 合併成一個大 .text，依此類推
```

### 9.1.2 連結的輸入與輸出

```
輸入：
  多個 .o 檔（可重定位目的碼）
  靜態程式庫 .a（.o 檔的 ar 封裝）
  動態程式庫路徑（.so / .dll，僅記錄名稱，不複製）
  連結器指令碼（ld script，指定記憶體佈局）

輸出（視情況）：
  可執行檔（ELF type = ET_EXEC）
  共享程式庫（ELF type = ET_DYN）
  可重定位目的碼（ld -r，合併多個 .o 但不完全連結）
```

## 9.2 符號解析（Symbol Resolution）

### 9.2.1 符號解析的流程

連結器從左到右掃描所有輸入的目的檔與程式庫：

```
維護三個集合：
  E（Examined）：已掃描的目的檔集合
  U（Undefined）：尚未解析的符號集合
  D（Defined）：已找到定義的符號集合

演算法（for 每個輸入檔 f）：
  若 f 是目的檔（.o）：
    將 f 加入 E
    for f 中的每個符號 s：
      若 s 是定義（非 UNDEF）：
        若 s 已在 D → 重複定義錯誤（強符號衝突）
        否則 → 加入 D，從 U 移除 s
      若 s 是 UNDEF：
        若 s 不在 D → 加入 U

  若 f 是靜態程式庫（.a）：
    for .a 中的每個成員模組 m：
      若 m 中有符號能解析 U 中的某個符號 → 將 m 視為 .o 處理
      否則 → 忽略 m（不加入連結）← 這是 .a 的「按需取用」特性！

結束時若 U 不為空 → 連結錯誤：undefined reference to 'xxx'
```

### 9.2.2 強符號與弱符號

```c
// 強符號（Strong Symbol）：一般的函式與已初始化的全域變數
int global_var = 10;        // 強符號
void my_func() { ... }      // 強符號

// 弱符號（Weak Symbol）：允許被同名強符號覆蓋
__attribute__((weak)) int default_handler() { return 0; }
// 若其他 .o 中有同名強符號 default_handler → 弱符號被覆蓋
// 若無 → 使用此弱符號的定義
```

**多重定義的規則（Linux/GNU ld）：**

| 情況 | 結果 |
|------|------|
| 兩個強符號同名 | 連結錯誤 |
| 一個強符號 + 一個弱符號 | 選強符號 |
| 兩個弱符號同名 | 任選其一（行為未定義）|
| 強符號 + COMMON 符號 | 選強符號 |

### 9.2.3 COMMON 符號（未初始化全域變數）

```c
// C 語言中未初始化的全域變數在目的碼中被標記為 COMMON
int shared_counter;   // COMMON 符號（非 .bss！）

// 多個 .o 可以定義同名的 COMMON 符號 → 連結器選最大的那個
// a.o：int x;（4 bytes COMMON）
// b.o：int x;（4 bytes COMMON）
// 連結後：只有一個 x（4 bytes，放在 .bss）

// 對比：若有初始值就是強符號（.data）
int y = 0;            // 強符號（.data，即使值為 0）
```

## 9.3 重定位（Relocation）

### 9.3.1 重定位的執行步驟

連結器確定所有區段的最終載入位址後，對每個重定位項目執行計算：

```
對每個重定位項目 (section, offset, symbol, type, addend)：

  1. 取得符號的最終位址 S = symtab[symbol].final_address
  2. 計算被重定位欄位的位址 P = section.load_address + offset
  3. 根據 type 計算填入值：
     R_X86_64_64     → 填入 S + addend（64-bit 絕對位址）
     R_X86_64_32     → 填入 (S + addend) & 0xFFFFFFFF
     R_X86_64_PC32   → 填入 S + addend - P（32-bit 相對位址）
     R_X86_64_PLT32  → 填入 PLT[symbol] + addend - P
  4. 將計算值以小端序寫入 P 所指的位置
```

### 9.3.2 重定位範例

```
假設連結後的記憶體佈局：
  .text 載入位址：0x0040_0000
  .data 載入位址：0x0060_0000

main.o 中：
  .text 偏移 0x0001：CALL printf（重定位項目）
  printf 在 .text 偏移 0x1234（假設）

計算：
  S = printf 的最終位址
    = 0x0040_0000（.text 基底）+ 0x1234 = 0x0040_1234
  P = CALL 指令 imm32 欄位的位址
    = 0x0040_0000 + 0x0001 = 0x0040_0001
  type = R_X86_64_PLT32，addend = -4

填入值 = S + addend - P
       = 0x0040_1234 + (-4) - 0x0040_0001
       = 0x122F

連結後機器碼：
  E8 2F 12 00 00（CALL，相對位移 0x122F）
```

### 9.3.3 .text 中的資料引用重定位

```asm
; 原始組語
    LEA RDI, [msg]    ; 引用 .data 中的 msg

; 組譯後（msg 位址未知，暫填 0）：
; 48 8D 3D 00 00 00 00   （LEA RDI, [RIP + 0]）

; 重定位記錄：
; section=.text, offset=3（disp32 的位置）, symbol=msg
; type=R_X86_64_PC32, addend=-4

; 連結後（msg 在 0x601000，LEA 指令在 0x401007）：
; disp32 = 0x601000 + (-4) - (0x401007 + 3)
;        = 0x601000 - 4 - 0x40100A
;        = 0x1FFFF2
; 48 8D 3D F2 FF 1F 00（正確的 RIP 相對位址）
```

## 9.4 靜態連結（Static Linking）

### 9.4.1 靜態程式庫（.a 檔案）

靜態程式庫（Archive）是多個 .o 檔的集合，以 `ar` 工具建立：

```bash
# 建立靜態程式庫
ar rcs libmylib.a module1.o module2.o module3.o

# 結構（ar 格式）：
# !<arch>      （魔術字串）
# module1.o    （成員 1）
# module2.o    （成員 2）
# module3.o    （成員 3）
# Symbol table（ar 內建的符號索引，加速查找）
```

```bash
# 靜態連結使用方式
gcc main.o -L. -lmylib -o program
# -L. → 搜尋路徑包含目前目錄
# -lmylib → 連結 libmylib.a（去掉 lib 前綴和 .a 後綴）
```

### 9.4.2 靜態連結的特性

```
優點：
  ✓ 產生的可執行檔完全獨立（不依賴外部 .so）
  ✓ 執行時無動態連結的載入開銷
  ✓ 可在沒有相應程式庫的系統上執行

缺點：
  ✗ 可執行檔體積較大（每個程式都複製一份程式庫程式碼）
  ✗ 程式庫更新時，所有使用它的程式都需要重新連結
  ✗ 記憶體中多個程式各有一份相同的程式庫程式碼（無法共享）
```

### 9.4.3 連結順序的重要性

```bash
# ❌ 錯誤：程式庫在目的檔之前
gcc -lmylib main.o -o program
# 連結器掃描 libmylib.a 時，U 集合還是空的
# → libmylib 中沒有任何模組被選入 → undefined reference！

# ✓ 正確：程式庫在所有引用它的目的檔之後
gcc main.o -lmylib -o program

# ✓ 若有相互依賴，重複指定程式庫
gcc main.o -la -lb -la -o program
# -la 引用 -lb 中的符號，-lb 又引用 -la 中的符號 → 列兩次
```

## 9.5 動態連結（Dynamic Linking）

### 9.5.1 動態連結的概念

動態連結（Dynamic Linking）將連結的部分工作延遲到**程式執行時**才進行：

```
靜態連結：
  連結時複製 → 可執行檔包含所有程式碼

動態連結：
  連結時只記錄「需要 libfoo.so 的 bar 函式」
  執行時由 動態連結器（ld-linux.so）：
    1. 找到 libfoo.so 並載入到記憶體
    2. 解析 bar 的位址
    3. 填入程式的 PLT/GOT
```

### 9.5.2 Position-Independent Code（PIC）

共享程式庫（.so）必須能載入到任意位址，因此需要 **PIC（位置無關程式碼）**：

```
問題：若程式碼寫死了絕對位址，
     兩個程式載入同一個 .so 到不同位址時，
     位址就會出錯。

解法：PIC 所有記憶體存取改為相對於 RIP 的偏移量，
     這樣不管載入到哪裡，相對距離不變。

編譯時加 -fPIC：
  gcc -fPIC -shared -o libfoo.so foo.c
```

```asm
; 非 PIC（絕對位址，不能用於 .so）
MOV EAX, [0x601000]    ; 硬寫絕對位址 → 只在固定載入位址有效

; PIC（RIP 相對定址）
MOV EAX, [RIP + var]   ; var 的位址 = RIP + 常數偏移
                        ; 不管載入到哪裡，偏移量固定 ✓
```

### 9.5.3 GOT — 全域偏移表（Global Offset Table）

GOT 是一個指標陣列，存放外部符號的實際位址，在執行時由動態連結器填入：

```
程式碼區段（.text）
  MOV RAX, [RIP + got_entry]   → 讀取 GOT 中對應的指標
            ↓
GOT（.got 區段）
  [got_entry] = 0x7f8c...      ← 動態連結器填入的 printf 實際位址
```

```
為什麼用 GOT 而不直接用 RIP 相對存取？

因為 .text 是唯讀的（共享），
不能在執行時修改 .text 中的位址，
GOT 在 .data 區段，每個 process 有自己的副本，可以修改。
```

### 9.5.4 PLT — 程序連結表（Procedure Linkage Table）

PLT 配合 GOT 實現函式呼叫的**延遲綁定（Lazy Binding）**：

第一次呼叫 `printf`：

```
CALL printf@PLT
│
▼
PLT[printf]:               ← 每個外部函式在 PLT 有一個小存根
    JMP [GOT[printf]]      ← 跳到 GOT 中 printf 對應的指標
    │                         第一次：GOT 中是 resolver 的位址
    ▼
resolver（動態連結器）：
    解析 printf 的真實位址
    GOT[printf] ← printf 的真實位址
    跳入 printf 執行

第二次呼叫 printf：
CALL printf@PLT
│
▼
PLT[printf]:
    JMP [GOT[printf]]      ← GOT 中已填入真實位址
    │
    ▼
printf（直接跳入，無額外開銷）
```

**PLT 存根的完整結構（每個函式 16 bytes）：**

```asm
; PLT[printf] 的機器碼：
printf@plt:
    JMP  QWORD [RIP + got_printf]  ; 跳到 GOT 中的位址
    PUSH index                      ; 壓入符號索引（供 resolver 使用）
    JMP  plt0                       ; 跳到 PLT[0]（resolver 入口）

; PLT[0]（動態連結器入口）：
plt0:
    PUSH QWORD [RIP + got_link_map] ; 壓入 link_map
    JMP  QWORD [RIP + got_dl_resolve]; 跳入動態連結器
```

### 9.5.5 動態連結的特性

```
優點：
  ✓ 可執行檔體積小（不含程式庫程式碼）
  ✓ 多個程式共享同一份 .so 的記憶體映射（節省 RAM）
  ✓ 程式庫更新時，所有程式自動使用新版本（ABI 相容前提下）

缺點：
  ✗ 啟動時有額外的載入和解析時間
  ✗ 依賴外部 .so，若不存在則無法執行
  ✗ .so 版本不相容可能導致「DLL Hell」
```

## 9.6 連結器指令碼（Linker Script）

### 9.6.1 什麼是連結器指令碼？

連結器指令碼（Linker Script）控制連結器的行為，包括：
- 各區段的載入位址與執行位址
- 區段的合併順序
- 符號的定義

```ld
/* 簡單的連結器指令碼（嵌入式系統常用） */

ENTRY(_start)                  /* 程式進入點 */

MEMORY {
    FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 512K  /* ROM */
    RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 128K  /* RAM */
}

SECTIONS {
    .text : {                  /* 程式碼放到 FLASH */
        *(.text)               /* 所有 .o 的 .text 合併 */
        *(.text.*)
        *(.rodata)
    } > FLASH

    .data : {                  /* 已初始化資料的執行位址在 RAM */
        *(.data)
    } > RAM AT > FLASH         /* 但儲存在 FLASH（開機時複製到 RAM）*/

    .bss : {                   /* 未初始化資料 */
        *(.bss)
        *(COMMON)
    } > RAM

    _stack_top = ORIGIN(RAM) + LENGTH(RAM);  /* 定義符號 */
}
```

### 9.6.2 VMA 與 LMA

```
VMA（Virtual Memory Address）：程式執行時的位址
LMA（Load Memory Address）  ：程式儲存在媒介（如 ROM）的位址

嵌入式系統中：
  .data 的 LMA 在 FLASH（上電時存放）
  .data 的 VMA 在 RAM（執行時存放）
  
  開機程式（Startup Code）負責將 .data 從 FLASH 複製到 RAM：
  
  extern uint32_t _data_start, _data_end, _lma_data;
  
  uint32_t *src = &_lma_data;
  uint32_t *dst = &_data_start;
  while (dst < &_data_end)
      *dst++ = *src++;
```

## 9.7 載入器（Loader）

### 9.7.1 載入器的任務

**載入器（Loader）** 是作業系統的一部份，負責將可執行檔從磁碟讀入記憶體並啟動執行。

```
載入流程：

1. 讀取 ELF Header，確認魔術字串、機器架構
2. 讀取 Program Header Table（PHT），找出所有 Loadable Segment
3. 用 mmap 將各 Segment 對應到虛擬記憶體：
     LOAD segment（含 .text）→ 對應為可讀 + 可執行（rx）
     LOAD segment（含 .data）→ 對應為可讀 + 可寫（rw）
4. 若是動態執行檔：
     找到 PT_INTERP segment（內含動態連結器路徑，如 /lib64/ld-linux-x86-64.so.2）
     啟動動態連結器，由它完成後續的動態連結
5. 初始化堆疊（Stack）、設定 argc/argv/envp
6. 跳到程式進入點（Entry Point，即 ELF Header 的 e_entry）
```

### 9.7.2 ELF 的兩種視角

ELF 同時服務連結器和載入器，因此有兩種視角：

```
連結視角（Section View）：用於連結器
┌──────────────────────────────┐
│  ELF Header                  │
│  .text（程式碼 section）      │
│  .rodata                     │
│  .data                       │
│  .bss                        │
│  .symtab                     │
│  .rela.text                  │
│  Section Header Table（SHT） │ ← 連結器使用
└──────────────────────────────┘

執行視角（Segment View）：用於載入器
┌──────────────────────────────┐
│  ELF Header                  │
│  Program Header Table（PHT） │ ← 載入器使用
│  LOAD Segment 1（rx）        │   .text + .rodata 合併
│  LOAD Segment 2（rw）        │   .data + .bss 合併
│  （選用）DYNAMIC Segment     │   動態連結資訊
└──────────────────────────────┘
```

### 9.7.3 Program Header Table

```c
typedef struct {
    uint32_t p_type;    // PT_LOAD / PT_DYNAMIC / PT_INTERP / PT_NOTE ...
    uint32_t p_flags;   // PF_X（執行）/ PF_W（寫）/ PF_R（讀）
    uint64_t p_offset;  // 在 ELF 檔案中的偏移
    uint64_t p_vaddr;   // 執行時的虛擬位址（VMA）
    uint64_t p_paddr;   // 物理位址（嵌入式用，一般 = vaddr）
    uint64_t p_filesz;  // 在檔案中的大小
    uint64_t p_memsz;   // 在記憶體中的大小（≥ filesz，.bss 補零）
    uint64_t p_align;   // 對齊要求（通常是頁面大小 0x1000）
} Elf64_Phdr;
```

**典型的可執行 ELF 的 PHT：**

```
索引  類型        VMA           FSz    MSz    旗標  對齊
 0    PT_PHDR    0x400040      0x268  0x268  R     0x8
 1    PT_INTERP  0x400268      0x1C   0x1C   R     0x1
       → /lib64/ld-linux-x86-64.so.2
 2    PT_LOAD    0x400000      0x6D4  0x6D4  R E   0x200000  ← .text（可讀+可執行）
 3    PT_LOAD    0x601E10      0x228  0x230  RW    0x200000  ← .data+.bss（可讀+可寫）
 4    PT_DYNAMIC 0x601E28      0x1D0  0x1D0  RW    0x8       ← 動態連結資訊
 5    PT_NOTE    0x400284      0x44   0x44   R     0x4
 6    PT_GNU_EH_FRAME ...                              ← 例外處理框架
 7    PT_GNU_STACK ...                    RW         ← 堆疊不可執行（安全）
```

### 9.7.4 記憶體映射（mmap）

現代作業系統使用 `mmap` 而非直接讀取，實現**按需載入（Demand Paging）**：

```
mmap 的好處：
  1. 多個程式使用同一個 .so → 在實體記憶體中只有一份
     （不同 process 的虛擬位址可以不同，但對應到同一個實體頁面）
  2. 按需載入：不立刻讀所有頁面，存取時才從磁碟讀入
  3. 節省記憶體：未被存取的程式碼頁面永遠不需載入

執行流程：
  mmap(vaddr=0x400000, size=0x6D4, prot=PROT_READ|PROT_EXEC,
       flags=MAP_PRIVATE, fd=exe_file, offset=0)
  → OS 僅建立虛擬記憶體映射，不立刻讀取
  
  程式執行到 0x400100 時發生 Page Fault：
  → OS 讀取 exe_file 中對應頁面到實體記憶體
  → 更新頁表，繼續執行
```

## 9.8 動態連結器（ld-linux.so）

### 9.8.1 動態連結器的啟動過程

```
核心的 execve() 系統呼叫完成後：
（execve 讀取 ELF Header，找到 PT_INTERP → /lib64/ld-linux-x86-64.so.2）

1. 核心載入 ld-linux.so 到記憶體（通常在高位址）
2. 核心將控制權交給 ld-linux.so 的 _start
3. ld-linux.so 執行以下動作：

   a. 讀取可執行檔的 PT_DYNAMIC，找出所需的 .so 列表（DT_NEEDED）
   b. 遞迴載入所有依賴的 .so：
      for each .so in DT_NEEDED:
          開啟 .so 檔
          mmap 到可用的虛擬位址
          讀取 .so 的 PT_DYNAMIC，繼續遞迴載入依賴
   c. 符號解析：掃描所有已載入的 .so 的符號表，填入 GOT
   d. 執行所有 .so 的初始化函式（.init / .init_array）
   e. 將控制權交給程式的進入點（e_entry）
```

### 9.8.2 共享程式庫的搜尋路徑

```
動態連結器搜尋 .so 的順序：

1. RPATH/RUNPATH（可執行檔內嵌的路徑）
2. LD_LIBRARY_PATH 環境變數（開發時常用）
3. /etc/ld.so.cache（由 ldconfig 建立的快取）
4. /lib64、/usr/lib64 等預設路徑

查看程式依賴的 .so：
  ldd ./my_program
  輸出：
    libm.so.6 => /lib/x86_64-linux-gnu/libm.so.6
    libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6
    /lib64/ld-linux-x86-64.so.2
```

## 9.10 本章小結

**連結器的三大任務：**
- 符號解析：從左到右掃描，維護 E/U/D 集合，解析 UNDEF 符號；強符號不能重複定義，弱符號可被覆蓋
- 重定位：確定各區段載入位址後，計算每個重定位項目的最終值（S+A-P 等公式）並填入
- 區段合併：所有 .o 的 .text 合併為一個大 .text，.data/.bss 同理

**靜態連結 vs 動態連結：**
- 靜態：程式庫程式碼複製進可執行檔，體積大、獨立、不可共享
- 動態：執行時由 ld-linux.so 載入 .so，體積小、可共享記憶體、依賴外部程式庫

**GOT / PLT 機制：**
- GOT 存放外部符號的執行時位址（可寫，每個 process 獨立副本）
- PLT 提供間接跳躍的小存根，第一次呼叫觸發 resolver，之後直接跳 GOT
- 延遲綁定（Lazy Binding）：只在第一次呼叫時解析，加速啟動

**載入器：**
- 讀取 PHT 中的 PT_LOAD，用 mmap 將各 Segment 對應到虛擬記憶體
- .bss 的 memsz > filesz，多餘部分由 OS 清零
- 按需載入：mmap 不立刻讀取，存取時 Page Fault 才觸發讀取
- PT_INTERP 指向動態連結器路徑，由 ld-linux.so 完成後續初始化
